# AGENTS.md — постоянные правила для Codex

Ты работаешь над **Rebecca Desktop Companion** — Windows-приложением с автономным пиксельным персонажем. Общайся с пользователем **на русском, понятным новичку языком**.

## Перед изменениями

1. Прочитай `README.md`, `SPEC.md`, `ARCHITECTURE.md`, `ROADMAP.md`.
2. Уточни текущий отмеченный этап и изучи уже существующие работающие файлы.
3. Исполняй **только явно запрошенный этап**. Не реализуй следующий этап без подтверждения пользователя.
4. Сначала коротко назови файлы, которые собираешься изменить, и что будет считаться успехом.

## Критически важные ограничения

- Программа **не использует AI/LLM**: никакого OpenAI API, Ollama, LangChain, Transformers, локальных/облачных моделей, автоматической установки или сетевых запросов ради интеллект-функций.
- Codex как инструмент **пишет код**, но **не входит в runtime** персонажа.
- Оставить **интерфейс `DialogueProvider` для будущего подключения**, но **не внедрять LLM-провайдер**, не подготавливать реальные API-клиенты или ключи без отдельного разрешения.
- Основное поведение, память, эмоции, перемещения и анимации — **локальные и независимые** от диалогового провайдера.
- Не добавлять зависимость, сборщик, сервис, интернет-доступ или сбор телеметрии «на будущее».
- Не читать файлы/переписки/экран пользователя, не устанавливать глобальные хуки и не посылать сообщения наружу без отдельного запроса.
- Не запускать чужие программы, не менять чужие окна и не эмулировать нажатия/клики.
- Даже после возможного появления ИИ-модуля он никогда не будет иметь прямого управления ОС.

## Архитектура

- Python 3.12+ + PySide6; структура из `ARCHITECTURE.md` **расширяется постепенно**, не создавай пустые модули заранее.
- Отделяй UI, автономный behavior engine, физику, диалоги, конфиг, интеграции.
- Движок (`core`) не должен импортировать Qt, Win32 или сетевые SDK.
- Не создавай один огромный скрипт, где смешаны окно, движения, взаимодействия, данные и настройки.
- Стабильные интерфейсы и минимальные изменения; не удаляй/не переписывай рабочие части без причины.
- Осмысленные названия функций; лаконичные комментарии там, где это необходимо.
- Для тестов поведения: fake clock, фиксированный RNG seed, чистые функции где возможно.

## Стратегия разработки

- Пользователь новичок в программировании и хочет **маленькие безопасные этапы**.
- После изменения: проверь синтаксис/импорт, запусти доступные тесты, опиши точную команду запуска, дай 2–4 конкретных ручных проверки.
- Если нет доступа к Windows GUI, **не утверждай, что проверил прозрачность, трей, несколько мониторов или поведение в играх**. Отдельно попроси пользователя проверить эти пункты.
- Если тест не запущен — так и скажи. Не маскируй ошибки.
- Если что-то сломалось, в следующем запросе **сначала исправь**, только затем расширяй функциональность.
- Не делай «большого рефакторинга заодно».
- Не проси пользователя вручную переписывать много кода: по возможности вноси правки сам.
- Не выполнять commit, push, deploy, установку в автозапуск или изменение системных настроек без отдельного разрешения.

## Формат ответа после этапа

1. **Сделано** — коротко, по делу.
2. **Файлы** — что создано/изменено.
3. **Запуск** — команды для Windows PowerShell.
4. **Проверка** — что точно должен увидеть пользователь.
5. **Тесты** — что выполнено и что не удалось проверить.
6. **Стоп** — дождись обратной связи; не начинай следующий этап.

## Приоритет качества

Правильный запуск, отсутствие перекрытия кликов по экрану, ненавязчивость персонажа и воспроизводимость важнее большого числа механик. В случае противоречия между roadmap и новой явной просьбой пользователя руководствуйся новой просьбой, но отдельно отметь влияние на план.
