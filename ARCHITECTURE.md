# ARCHITECTURE — модули и контракты

## 1. Общая схема

```text
                  Пользователь / Windows
                          |
             [PySide6: компактное окно]
                 |             |
           ввод мыши      рисование спрайта
                 |             ^
                 v             |
              EventBus -> CharacterController
                               |
                  +------------+------------+
                  |            |            |
             World/Physics  Behavior      DialogueManager
                  |         Engine          |
                  |            |      DialogProvider (протокол)
                  |        CharacterState    |
                  |            |             +-> ScriptedProvider [активен]
                  |            |             +-> LLMProvider [не реализован]
                  +--------- Persistence/Config
                               |
                           local files

                optional later: Win32 / weather / app events
```

**Запрет зависимости:** `core/` не импортирует `PySide6`, `win32`, сетевые SDK или код хранения. UI подписывается на события и визуализирует уже выбранное действие. Провайдер диалога не изменяет игровые параметры напрямую.

## 3. Основные объекты и данные

### `CharacterState`

Только данные (dataclass/typed model, без Qt):

```text
energy: float          0..100
boredom: float         0..100
irritation: float      0..100
affinity: float        0..100
curiosity: float       0..100
current_action: enum
mode: enum             autonomous | paused | dragged | hidden
position: {screen_id, x, y}       # x/y в координатах Qt
velocity: {vx, vy}
action_started_at: monotonic_time
action_cooldown_until: monotonic_time
last_interaction_at: wall_time
```

Хранить **только необходимые поля**; добавить новые после новых механик. Значения ограничивать диапазоном 0..100. `monotonic_time` служит для таймеров текущего запуска, **не записывается в постоянное хранилище**. Для длительных периодов использовать UTC timestamps, обрабатывая возможный сдвиг системного времени.

### События

Начальный перечень:

```text
Tick(dt)
PointerClicked(screen_x, screen_y)
DragStarted / DragMoved / DragEnded
ActionFinished(action)
IdleTimeout
ScreenGeometryChanged
PauseRequested / ResumeRequested / HideRequested / ExitRequested
```

Позднее: `WindowGeometryChanged`, `FullScreenStarted`, `AppActivated`, `WeatherUpdated` (с consent).

### Приоритеты действий

1. Служебные состояния `paused`, `hidden`, завершение работы.
2. Владелец ручного управления `dragged` (его нельзя перебить «я захотела поспать»).
3. Безопасность позиции: падение, выход за рабочую область, удаление платформы.
4. Непосредственные реакции пользователя (ограничены по частоте).
5. Потребности: сон, отдых, прогулка.
6. Редкие активности, любопытство, случайные действия.

Игра не должна дёргаться между `sleep` и `walk`: вводить минимальную длительность действий, сдерживающие пороги (hysteresis), кулдауны и вероятность выбора.

## 4. Выбор действий — автономность без нейросетей

**Рекомендуемый алгоритм:** конечный автомат (`FSM`) для исполнения действия + простая функция оценки полезности (`utility scoring`) для выбора следующего.

Пример (значения и коэффициенты условные):

```text
score(sleep) = (100 - energy) * 1.6 + night_bonus
score(explore) = boredom * 0.9 + curiosity * 0.4
score(idle) = 35 + low_boredom_bonus
score(approach_cursor) = boredom * 0.5 + affinity * 0.2 - irritation
```

Кандидаты исключаются по условиям (невозможность движения, нет анимации, cooldown, не в зоне). Между близкими оценками вносится небольшой seeded-random, чтобы поведение не было роботизированным; выбор всегда подчиняется ограничениям. Сильные события (drag/drop) имеют приоритет выше utility scoring.

**Параметры:** физика до 30 визуальных кадров/сек (по Qt таймеру с dt и ограничением), пересчёт потребностей примерно раз в секунду, решений — ориентировочно раз в 1–3 секунды или по значимому событию. Частоту проверить профилированием; Qt UI не блокировать `sleep`.

### Пример цепочки

```text
idle -> скука накопилась -> explore -> walk -> достигла границы
  -> idle -> наблюдает курсор -> react (1 сек) -> idle
```

После 5 кликов за короткое время:

```text
click -> irritation+ -> react_annoyed -> cooldown
```

Пока cooldown активен, повторные клики могут обновлять счётчик раздражения, но **не порождают 5 перекрывающихся анимаций и реплик**.

## 5. Физика, позиции и окна

### P0/P1

- Координаты: Qt global logical pixels; явное преобразование для размера пиксельного арта с учётом DPI.
- Опорная точка: ноги персонажа; спрайт расположен относительно неё.
- Границы: `QScreen.availableGeometry()` выбранного экрана (в том числе исключение панели задач).
- Движение: ускорение/скорость в логических пикселях в секунду; вычислять по `dt`, не «по кадрам».
- При drag использовать глобальные координаты мыши и запомнить офсет захвата; при отпускании — clamp к экрану и восстановление состояния.
- Если `QScreen` недоступен, fallback на основной экран.
- Масштабировать pixel-art через `nearest-neighbor`, не размывать.

### P2

Для физических «платформ» поверх чужих окон выделить `WindowPlatformProvider`, который отдаёт **только прямоугольники видимых пригодных окон** (без содержимого). Учитывать виртуальный рабочий стол, Z-order, свёрнутые/скрытые окна, DPI, изменяющиеся размеры. Временно удалённая платформа не должна вызывать аварийный teleport или падение приложения. Не начинать эту систему в MVP.

**Замечание Windows:** рабочая область каждого монитора отличается; `SPI_GETWORKAREA` относится к основному монитору, для других нужны данные отдельного монитора (в Qt `QScreen.availableGeometry`, в Win32 `GetMonitorInfo`).

## 6. GUI и пропускание ввода

- `QWidget` с `Qt.FramelessWindowHint` и `Qt.WA_TranslucentBackground`; по настройке `Qt.WindowStaysOnTopHint`.
- Прозрачная **не значит click-through**. Для интерактивного персонажа **не** использовать `Qt.WindowTransparentForInput` на основном окне: тогда нельзя будет её взять мышью.
- Окно должно быть **по размеру персонажа**, а не как весь монитор. При желании позже использовать shape/mask и проверить качество нативного hit-test на Windows.
- По левому клику реакция; при drag — перемещение; по правому — меню; события мыши не должны попадать в чужие окна в момент взаимодействия с персонажем.
- Реплики показывать в отдельном компактном bubble-окне рядом, без фокуса до явного открытия диалога.
- Рядом с персонажем пользователь должен свободно взаимодействовать с другими окнами.
- `QSystemTrayIcon` — отдельный аварийно-доступный способ паузы/выхода.

## 7. Локальная память и настройки

Рекомендуемый путь — `QStandardPaths.AppDataLocation` / `%LOCALAPPDATA%/RebeccaDesktopCompanion/`; не хранить изменяемые данные рядом с exe.

- `settings.json` — версия схемы, масштаб, громкость, topmost, частота реакций, автономность, автоскрытие, разрешения интеграций.
- `state.json` или SQLite — последняя корректная позиция и 4–5 числовых параметров.
- `memory.sqlite` (позднее) — ограниченная история событий и предпочтения, например:
  - `event_summary(ts_utc, category, data_json)` — максимум 500 последних записей;
  - `habit_weights(context_key, action_key, weight)`;
  - `dialogue_history(ts_utc, intent_id, response_id)` — максимум 100 записей.

На MVP хватит одного JSON для конфигурации и состояния; **не подключать SQLite раньше реальной потребности**. Запись конфигурации делать атомарно или через временный файл/замену. Версионировать схему и предусмотреть миграции. Не сохранять каждый кадр. Настройки — при изменении, состояние — при безопасном выходе/редко по таймеру.

## 8. Диалоги, разделение провайдеров, будущая LLM

Заложить протокол, но **не подключать ни SDK, ни сеть**:

```python
@dataclass
class DialogueRequest:
    intent: str | None              # topic id / команда, или свободный текст в будущем
    user_text: str | None
    locale: str
    context: dict[str, object]      # только разрешённые поля состояния

@dataclass
class DialogueResponse:
    text: str
    emotion: str | None = None
    animation: str | None = None

class DialogueProvider(Protocol):
    def respond(self, request: DialogueRequest) -> DialogueResponse: ...
```

В P1 реализовать `ScriptedDialogueProvider`: выбирает случайную фразу из локального каталога по известному `intent`, эмоциям, cooldown и истории. При отсутствии ответа — заранее прописанный fallback. Пример содержимого `assets/dialogues/ru.json`:

```json
{
  "how_are_you": {
    "neutral": ["Да нормально, чумба. Чего хотел?", "Скучновато тут сегодня."],
    "irritated": ["Не сейчас. Я не в настроении."]
  },
  "go_sleep": {
    "neutral": ["Ладно, немного отдохну."],
    "sleepy": ["Вот это дельное предложение!"]
  }
}
```

### Позднее, **только по отдельному решению пользователя**

`LLMDialogueProvider` как опциональная реализация **того же протокола**:

1. Выключен в конфиге (`dialogue.provider="scripted"`, `llm.enabled=false`).
2. Отдельно устанавливаемая зависимость и конфигурация; основные действия не зависят от API.
3. Используется только для текста и **подсказки** эмоции/анимации из allowlist; вся физика/мышь/ОС остаются под управлением локального контроллера.
4. Таймаут и fallback на `ScriptedDialogueProvider` при любой ошибке, недоступности сети или отключении функции.
5. Никаких инструментов модели с правами чтения файлов, управления мышью, запуска программ, снимка экрана или получения ключей.
6. Контекст минимален, пользователь видит, что передаётся; диалоговые истории отправляются только после согласия.
7. API-ключи не писать в JSON проекта и Git; использовать защищённое хранение/переменные окружения.
8. Не создавать и не импортировать реальный модуль LLM в MVP, пока достаточно интерфейса и тестового mock-провайдера.

**Принцип:** интеграция меняет лишь способ генерации реплики, **не сердце персонажа**.

## 10. Тестирование и качество

Автоматические тесты (без GUI): ограничения характеристик, отсутствие спама, неподвижность во время drag, корректный выбор действия, отсутствие запланированной модели, сериализация, fallback диалогов, выход за границы экрана. Тесты с fake-clock (вместо настоящего ожидания), seed для RNG, фиктивным репозиторием памяти и провайдером окон.

GUI-тесты вручную **на Windows**: прозрачность, отсутствие рамки, фокус, drag, контекстное меню, трей, много экранов, масштаб Windows 125–200%, перезапуск, отключение одного монитора, работа офлайн, запуск полноэкранной игры после реализации P1.

Проверять нагрузку CPU/RAM на протяжении хотя бы 10–15 минут, а при утечках — более длительно. Паковать exe лишь после успешного поведения из исходников.

## 11. Технический долг, который нужно предотвращать

- Никаких монолитных скриптов на сотни строк со смешением окна, физики, эмоций и базы.
- Не редактировать много стабильных модулей ради одной анимации.
- Не плодить `QTimer` на каждую систему без единого управления.
- Не вызывать тяжёлые функции в `paintEvent`.
- Не тянуть сетевые зависимости в `core`.
- Не тестировать UI только автоматикой: пользователь должен подтвердить работу на своём Windows.
